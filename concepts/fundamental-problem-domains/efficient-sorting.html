Beyond Quadratic Sorting

Quicksort is not the only way to sort faster than O(n2)O(n^2)O(n2). Each of the three basic ideas (exchange, insertion and selection) has an efficient counterpart, and there are also algorithms based on completely different principles. This lesson presents the most important ones, explains the theoretical limit that all comparison-based algorithms share, and shows how some algorithms manage to go below that limit.

What you will learn in this lesson
  • Shellsort, which improves insertion by moving elements over long distances first.
  • Heapsort, which improves selection by using a heap, and guarantees O(nlog⁡n)O(n \log n)O(nlogn) in place.
  • Mergesort, which sorts by merging, guarantees O(nlog⁡n)O(n \log n)O(nlogn) and is stable.
  • Why no algorithm based on comparisons can beat O(nlog⁡n)O(n \log n)O(nlogn) in the worst case.
  • Counting and radix sort, which sort in linear time by not comparing elements at all.
  • What the sorting methods of real libraries use.

Shellsort: Insertion over Long Distances​

Insertion sort is slow on random data because it moves elements one position at a time, removing a single inversion per shift. Donald Shell proposed (in 1959) to apply insertion sort first to elements that are far apart, so that elements can travel long distances in a few moves, and then progressively reduce the distance.

The algorithm uses a decreasing sequence of gaps (increments) h1>h2>⋯>ht=1h_1 \gt h_2 \gt \cdots \gt h_t = 1h1​>h2​>⋯>ht​=1. For each gap hhh, it performs an insertion sort on each of the subsequences formed by elements hhh positions apart (the vector becomes "hhh-sorted"). The last pass, with h=1h = 1h=1, is an ordinary insertion sort, which guarantees that the result is sorted; but by then the vector is almost sorted, and insertion sort is very fast on almost sorted data.

public void sort(int[] elements) {
    int n = elements.length;
    for (int gap = n / 2; gap > 0; gap /= 2) {          // gaps n/2, n/4, ..., 1
        for (int i = gap; i < n; i++) {                 // insertion sort with step "gap"
            int key = elements[i];
            int j = i - gap;
            while (j >= 0 && key < elements[j]) {
                elements[j + gap] = elements[j];
                j -= gap;
            }
            elements[j + gap] = key;
        }
    }
}

The analysis of Shellsort is notoriously difficult and depends on the gap sequence. With Shell's original sequence (n/2,n/4,…n/2, n/4, \dotsn/2,n/4,…), the worst case is still O(n2)O(n^2)O(n2); with better sequences, such as Knuth's (1,4,13,40,…1, 4, 13, 40, \dots1,4,13,40,…, each one three times the previous plus one), the worst case is O(n3/2)O(n^{3/2})O(n3/2), and some sequences achieve even better bounds. In practice, Shellsort is fast for medium-sized arrays, very short to implement and in place, but it is not stable (elements jump over others that may have equal keys). With n=10,000n = 10{,}000n=10,000 random elements and Shell's gaps, it performed about 260,000 comparisons in our tests, compared with about 25 million for insertion sort.

Heapsort: Selection with a Heap​

Selection sort spends linear time finding each maximum (or minimum). Heapsort keeps the unsorted part organized as a heap, which provides the maximum immediately and can be repaired in logarithmic time.

Binary heaps​

A max-heap is a complete binary tree in which every node is greater than or equal to its children, so the maximum is always at the root. A complete binary tree can be stored in an array without any pointers: the root is at position 0, and the children of the node at position iii are at positions 2i+12i + 12i+1 and 2i+22i + 22i+2. The height of the tree is about log⁡2n\log_2 nlog2​n.

The key operation is sinking (down-heap): if a node is smaller than one of its children, it is exchanged with its larger child, and the process continues downwards until the heap property is restored. It costs at most one step per level: O(log⁡n)O(\log n)O(logn).

The algorithm​

  1. Build a heap with all the elements, sinking every internal node from the last one up to the root. (This phase costs only O(n)O(n)O(n), a remarkable result.)
  2. Repeat n−1n - 1n−1 times: exchange the root (the maximum) with the last element of the heap, reduce the size of the heap by one (the maximum is now in its final position at the end of the array), and sink the new root to restore the heap.
public void sort(int[] elements) {
    int n = elements.length;
    for (int i = n / 2 - 1; i >= 0; i--)        // 1. build the heap
        downHeap(elements, i, n);
    while (n > 1) {                             // 2. extract the maximum n - 1 times
        n--;
        Util.swap(elements, 0, n);              // the maximum goes to its final position
        downHeap(elements, 0, n);               // restore the heap in elements[0..n-1]
    }
}

private void downHeap(int[] elements, int parent, int heapSize) {
    int child = 2 * parent + 1;                 // left child
    while (child < heapSize) {
        if (child + 1 < heapSize && elements[child + 1] > elements[child])
            child++;                            // the larger of the two children
        if (elements[parent] >= elements[child])
            break;                              // the heap property holds
        Util.swap(elements, parent, child);
        parent = child;
        child = 2 * parent + 1;
    }
}

Heapsort is O(nlog⁡n)O(n \log n)O(nlogn) in all cases (best, worst and average), in place, but not stable. Its running time is very predictable: in the table of the course slides, its times for sorted, random and reverse inputs are almost identical. In practice it is usually slower than Quicksort, because its accesses jump around the array (parent to child), which uses the processor cache poorly. It is used as a safety net in Introsort, and heaps are, in their own right, the structure behind PriorityQueue.

Mergesort: Sorting by Merging​

Mergesort is based on a different idea: merging two sorted sequences into a single sorted sequence is easy and fast, since it only requires comparing the first elements of both and taking the smaller one, repeatedly. So:

  1. Divide the vector into two halves.
  2. Sort each half, recursively.
  3. Merge the two sorted halves.
private void mergeSort(int[] elements, int[] aux, int left, int right) {
    if (left < right) {
        int center = left + (right - left) / 2;
        mergeSort(elements, aux, left, center);
        mergeSort(elements, aux, center + 1, right);
        merge(elements, aux, left, center, right);     // linear in (right - left + 1)
    }
}

The recursion always divides the vector into halves, regardless of the data, so there are always about log⁡2n\log_2 nlog2​n levels, each with a total merging cost of O(n)O(n)O(n). Mergesort is therefore O(nlog⁡n)O(n \log n)O(nlogn) in all cases, like Heapsort, and, unlike Quicksort and Heapsort, it is stable (when the two candidates are equal, the merge takes the one from the left half). Its drawback is memory: merging arrays requires an auxiliary array of size nnn, so it is not in place.

Mergesort is a classic example of divide and conquer, and you will study it in detail (with its recurrence, its variants and its applications) in that chapter. It is also the basis of external sorting algorithms (see the next lesson) and of TimSort, the algorithm used by Java to sort objects and by Python to sort lists.

The Limit of Comparison-Based Sorting​

All the algorithms we have seen so far sort by comparing pairs of elements. Can such an algorithm be faster than O(nlog⁡n)O(n \log n)O(nlogn)? The answer is no, and the argument is one of the most elegant results in computer science.

Any comparison-based algorithm can be represented as a decision tree: each internal node is a comparison ("is ai<aja_i \lt a_jai​<aj​?"), and the two branches correspond to its two possible outcomes. Each leaf is a final arrangement of the input. Then:

  • To sort correctly, the algorithm must be able to produce every possible order of the input, so the tree needs at least n!n!n! leaves (one per permutation).
  • A binary tree of height hhh has at most 2h2^h2h leaves, so 2h≥n!2^h \ge n!2h≥n!, that is, h≥log⁡2(n!)h \ge \log_2 (n!)h≥log2​(n!).
  • The height hhh is the number of comparisons in the worst case, and log⁡2(n!)\log_2(n!)log2​(n!) grows like nlog⁡2nn \log_2 nnlog2​n (more precisely, log⁡2(n!)≈nlog⁡2n−1.44 n\log_2(n!) \approx n \log_2 n - 1.44\,nlog2​(n!)≈nlog2​n−1.44n).

Every comparison-based sorting algorithm needs Ω(nlog⁡n)\Omega(n \log n)Ω(nlogn) comparisons in the worst case.

This is a statement about the problem, not about a particular algorithm: no one will ever find a comparison-based algorithm that does better. Heapsort and Mergesort, which are O(nlog⁡n)O(n \log n)O(nlogn) in the worst case, are therefore asymptotically optimal.

Sorting Without Comparisons​

The lower bound only applies to algorithms that obtain information exclusively by comparing elements. If we know something more about the keys (for example, that they are integers in a small range), we can do better.

Counting sort and Binsort​

If the keys are integers between 000 and k−1k - 1k−1, we can count how many times each value appears, using an array of kkk counters, and then write each value as many times as it was counted (or, for records, compute the final position of each one from the counts). This takes O(n+k)O(n + k)O(n+k) time and O(k)O(k)O(k) extra memory: linear when kkk is O(n)O(n)O(n). The related Binsort (bucket sort) distributes the elements into "bins" according to their key and then concatenates the bins.

Radix sort​

Radix sort sorts integers digit by digit, from the least significant to the most significant. In each pass, it distributes the elements into 10 queues (one per digit value) according to the current digit, and then collects them in order. Because each pass is stable, the order established by the previous digits is preserved among elements with the same current digit.

With ddd digits per key, radix sort performs ddd passes of O(n)O(n)O(n) each: O(d⋅n)O(d \cdot n)O(d⋅n). For keys with a bounded number of digits, this is linear in nnn. The price is extra memory for the queues, and the restriction to keys that can be decomposed into digits (integers, fixed-length strings...).

Negative numbers

The simple radix sort above assumes non-negative integers. In Java, -1 % 10 is -1, so a negative number produces a negative "digit" and an invalid queue index. To support negative values, the usual solutions are to sort negative and non-negative numbers separately, or to add an offset to all the keys.

What Real Libraries Use​

Real sorting libraries combine several algorithms to get the best of each:

  • Java, primitive types (Arrays.sort(int[]), etc.): a dual-pivot Quicksort, with insertion sort for small parts. Stability does not matter for primitives, and Quicksort is the fastest in practice.
  • Java, objects (Arrays.sort(Object[]), Collections.sort, List.sort): TimSort, a hybrid of Mergesort and insertion sort that detects already sorted runs in the data. It is stable, which is essential for objects, and very fast on partially sorted data.
  • Python (sorted, list.sort): TimSort as well (it was designed for Python).
  • C++ (std::sort): typically Introsort (Quicksort + Heapsort + insertion sort), and std::stable_sort for a stable sort.

The lesson is that there is no single "best" sorting algorithm: each one has strengths, and good engineering combines them.
