# Proofs: Sorting

This page proves the claims made in the sorting lessons: that each algorithm sorts correctly, the costs given in the lessons, and the limits that no comparison-based algorithm can break. The proofs use loop invariants and induction, explained in [Induction, Correctness and Recurrences](../06-mathematical-background/02-induction-and-recurrences.mdx). Arrays are indexed from 0 and have $n$ elements.

***

## Bubble sort is correct

The [bubble sort](./02-bubble-sort.mdx) of the lessons performs passes $i = 1, \dots, n - 1$; each pass scans from the right end down to position $i$, swapping adjacent elements that are out of order.

*Invariant.* After pass $i$, the positions $0, \dots, i - 1$ hold the $i$ smallest elements, in order.

*Proof.* During pass $i$, the scan carries a minimum $m$ of `elements[i-1..n-1]` to position $i - 1$. From the moment the scan meets a copy of $m$, the element at the current scan position is always equal to $m$: if its left neighbor is larger, they are swapped; if the neighbor is also equal to $m$, the scan simply continues with that copy. Before the pass, by the invariant for $i - 1$, positions $0, \dots, i - 2$ hold the $i - 1$ smallest elements in order, and the pass never touches them. So after the pass, position $i - 1$ holds the smallest of the rest, which is the $i$-th smallest overall. After pass $n - 1$, the first $n - 1$ positions hold the $n - 1$ smallest in order, and the last position holds the largest: the array is sorted. $\blacksquare$

**The sentinel.** If a pass makes no swap, every pair of adjacent elements in `elements[i-1..n-1]` is in order, so that part is sorted; together with the invariant, the whole array is sorted, and stopping is correct.

## Insertion sort is correct

*Invariant.* Before processing position $i$, the subarray `elements[0..i-1]` contains the original first $i$ elements, in order.

*Proof.* For $i = 1$, a single element is sorted. When position $i$ is processed, the key `elements[i]` is saved, and the elements of the sorted prefix that are **greater** than the key are shifted one position to the right, starting from the end, until an element not greater than the key (or the start of the array) is found. The key is written in the gap. The elements to the left of the gap are at most the key, those to its right are greater, and both groups keep their order: `elements[0..i]` is sorted. At the end ($i = n$) the whole array is sorted. $\blacksquare$

Because the loop stops at the first element **not greater** than the key, equal elements are never moved past each other: insertion sort is **stable**.

***

## Selection sort is correct

*Invariant.* After iteration $i$, positions $0, \dots, i$ hold the $i + 1$ smallest elements, in order.

*Proof.* Iteration $i$ finds the minimum of `elements[i..n-1]` and swaps it into position $i$. By the invariant for $i - 1$, everything before position $i$ is smaller than or equal to everything from $i$ on, so the minimum of the rest is the $(i+1)$-th smallest element. After iteration $n - 2$, the last element is the largest. $\blacksquare$

The number of comparisons does not depend on the input: $\sum_{i=0}^{n-2} (n - 1 - i) = \frac{n(n-1)}{2}$.

***

## Adjacent swaps need quadratic time

The [bubble sort lesson](./02-bubble-sort.mdx#inversions-why-adjacent-swaps-are-slow) argues that algorithms that only swap adjacent elements are slow. Here is the proof.

**Claim 1.** Swapping two adjacent elements changes the number of inversions by exactly one.

*Proof.* An inversion is a pair of positions $i \lt j$ with $a_i \gt a_j$. Swapping $a_k$ and $a_{k+1}$ does not change the relative order of any pair except that pair itself. So the number of inversions changes by exactly one: it decreases if they were out of order, and increases otherwise. $\blacksquare$

A sorted array has no inversions, so any algorithm that only swaps adjacent elements performs at least $I$ swaps, where $I$ is the number of inversions of the input.

**Claim 2.** A random permutation of $n$ distinct elements has $\frac{n(n-1)}{4}$ inversions on average.

*Proof.* Each of the $\binom{n}{2} = \frac{n(n-1)}{2}$ pairs of positions is an inversion in exactly half of the permutations: reversing a permutation turns each inversion into a non-inversion and vice versa. So each pair contributes $\frac{1}{2}$ to the expected count. $\blacksquare$

Combining both: bubble sort, insertion sort and any other algorithm based on adjacent swaps need $\Omega(n^2)$ swaps **on average**, not only in the worst case. Efficient algorithms must move elements over long distances, as Shellsort, Heapsort, Mergesort and Quicksort do.

***

## No comparison sort can beat n log n

**Claim.** Every sorting algorithm that only obtains information by comparing elements needs at least $\lceil \log_2 (n!) \rceil$ comparisons in the worst case, which is $\Omega(n \log n)$.

*Proof.* Represent the algorithm, for a fixed $n$, as a **decision tree**: each internal node is a comparison "is $a_i \lt a_j$?", its two children are the two possible outcomes, and each leaf is the moment the algorithm finishes, having determined the order of the input. Two different permutations of distinct elements must reach different leaves, because they require different rearrangements. So the tree has at least $n!$ leaves. A binary tree of height $h$ has at most $2^h$ leaves, so $2^h \ge n!$ and

$$
h \ge \log_2 (n!) \ge \log_2 \left( \left( \frac{n}{2} \right)^{n/2} \right) = \frac{n}{2} \log_2 \frac{n}{2}
$$

using that the largest $n/2$ factors of $n!$ are each at least $n/2$. The height is the number of comparisons in the worst case. $\blacksquare$

The same argument applied to the **average** depth of the leaves shows that the bound also holds on average. Mergesort and Heapsort, with $O(n \log n)$ in the worst case, are therefore **asymptotically optimal**. Algorithms such as counting sort and radix sort escape the bound because they do not only compare: they use the values as array indices.

## Quicksort's partition is correct

The [Quicksort of the lessons](./05-quicksort.mdx#the-partitioning-strategy) hides the pivot at the end of the range and moves two indices, `i` from the left and `j` from the right.

*Invariant.* At every moment, all elements to the left of `i` are at most the pivot, and all elements to the right of `j` (and before the hidden pivot) are at least the pivot.

*Proof.* Initially both regions are empty. The first inner loop advances `i` over elements at most the pivot, and the second moves `j` back over elements at least the pivot, which keeps the invariant. When both stop with `i < j`, `elements[i]` is greater than the pivot and `elements[j]` is smaller; swapping them extends both regions. When the indices cross, every element before `i` is at most the pivot and every element from `i` on is at least the pivot, so swapping the pivot into position `i` puts it in its **final** position. $\blacksquare$

Quicksort is then correct by strong induction on the size: both recursive calls receive smaller ranges (the pivot is excluded), sort them by the induction hypothesis, and the pivot between them is already in place.

## The average cost of Quicksort

**Claim.** If the pivot is chosen uniformly at random (or the input is a random permutation and the pivot is any fixed position), Quicksort performs on average

$$
C(n) = 2(n+1) H_n - 4n \approx 2 n \ln n \approx 1.39 \, n \log_2 n
$$

comparisons, where $H_n = 1 + \frac{1}{2} + \dots + \frac{1}{n}$.

*Proof.* Partitioning $n$ elements takes $n - 1$ comparisons with the pivot. If the pivot ends up at position $k$ (each $k$ from $0$ to $n-1$ with probability $1/n$), the two parts have sizes $k$ and $n - 1 - k$. So

$$
C(n) = n - 1 + \frac{1}{n} \sum_{k=0}^{n-1} \left( C(k) + C(n-1-k) \right) = n - 1 + \frac{2}{n} \sum_{k=0}^{n-1} C(k)
$$

with $C(0) = C(1) = 0$. Multiply by $n$, write the same equation for $n - 1$, and subtract:

$$
n C(n) - (n-1) C(n-1) = 2(n-1) + 2 C(n-1) \quad\Longrightarrow\quad n C(n) = (n+1) C(n-1) + 2(n-1)
$$

Dividing by $n(n+1)$, the quantity $D(n) = \frac{C(n)}{n+1}$ satisfies $D(n) = D(n-1) + \frac{2(n-1)}{n(n+1)}$, and since $\frac{2(k-1)}{k(k+1)} = \frac{4}{k+1} - \frac{2}{k}$, the sum telescopes into

$$
D(n) = \sum_{k=1}^{n} \left( \frac{4}{k+1} - \frac{2}{k} \right) = 2 H_n - 4 + \frac{4}{n+1}
$$

Multiplying back by $n + 1$ gives the formula. We checked it with exact rational arithmetic against the recurrence for every $n$ up to 29; for $n = 10$ it gives about 24.4 comparisons. Since $H_n \approx \ln n$, the cost is $\Theta(n \log n)$, only 39% above the lower bound. $\blacksquare$

The median-of-three pivot of the lessons reduces the constant further (to about $1.19 \, n \log_2 n$) but the analysis is more involved.

## Mergesort is correct and costs n log n

*Merge.* The merge of two sorted halves repeatedly copies the smaller of their first remaining elements. Invariant: the output written so far contains the smallest elements of both halves, in order. Each step preserves it, because the smallest remaining element of the union is the first remaining element of one of the halves. When one half is exhausted, the rest of the other half is copied, and it is already sorted and not smaller than anything written. So the merge is correct. Taking the element of the **left** half when two are equal makes Mergesort stable.

*Cost.* Merging $n$ elements takes at most $n - 1$ comparisons and exactly $n$ copies, so $T(n) = 2T(n/2) + \Theta(n)$, which is $\Theta(n \log n)$ by the [division formula](../03-algorithm-design-paradigms/proofs.mdx#the-division-formula). The recursion tree has $\log_2 n$ levels and each level copies all $n$ elements once. $\blacksquare$

## Building a heap takes linear time

**Claim.** The first phase of [Heapsort](./06-efficient-sorting.mdx#heapsort-selection-with-a-heap), which calls `downHeap` on positions $n/2 - 1$ down to 0, takes $O(n)$ time, not $O(n \log n)$.

*Proof.* `downHeap` on a node at height $h$ (distance to the deepest leaf below it) performs at most $h$ swaps. A heap with $n$ nodes has at most $\lceil n / 2^{h+1} \rceil$ nodes at height $h$. So the total work is at most

$$
\sum_{h=0}^{\lfloor \log_2 n \rfloor} \left\lceil \frac{n}{2^{h+1}} \right\rceil h \;\le\; n \sum_{h=0}^{\infty} \frac{h}{2^{h+1}} + O(\log^2 n) = n + O(\log^2 n)
$$

using $\sum_{h \ge 0} h / 2^h = 2$. Most nodes are near the bottom, where `downHeap` is cheap. $\blacksquare$

The second phase extracts the maximum $n - 1$ times, each with a `downHeap` from the root, at most $\log_2 n$ swaps each: $O(n \log n)$. So Heapsort is $O(n \log n)$ in every case.

## Radix sort is correct

The least-significant-digit [radix sort](./06-efficient-sorting.mdx#radix-sort) sorts the numbers by their last digit, then by the next one, and so on, with a **stable** sort at each step (counting sort or buckets).

*Invariant.* After $d$ passes, the numbers are sorted by their last $d$ digits (as numbers formed by those digits).

*Proof.* By induction on $d$. Pass $d + 1$ sorts by digit $d + 1$ (counting from the right). Two numbers with different digits there end up in the right order by that digit, which decides the comparison of their last $d + 1$ digits. Two numbers with the **same** digit keep their previous relative order, because the pass is stable, and by the induction hypothesis that order was correct for the last $d$ digits. After as many passes as the numbers have digits, they are fully sorted. $\blacksquare$

Stability is essential: with an unstable sort in each pass, the order established by the previous passes would be lost.
