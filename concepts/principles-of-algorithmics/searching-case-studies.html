Case Studies: Searching

⏱ 16 min readRead first: Data Structures · Complexity of Loops

Searching is one of the most frequent operations in computing: looking up a user in a database, a word in a dictionary, a file in a directory, a value in a cache. In this final lesson of the chapter we apply everything we have learnt to three classic search algorithms. For each one we count instructions exactly, analyze the best, worst and average cases, express the result with asymptotic notation and connect it with real measurements.

The problem is simple to state:

  • Input: a sequence AAA of nnn integers and a value xxx.
  • Output: true if xxx appears in AAA, and false otherwise.
What you will learn in this lesson
  • How to count the exact cost of sequential search in its best, worst and average cases, including a complete average-case derivation.
  • How the sentinel technique reduces the constant of an algorithm without changing its complexity, and what it costs.
  • How binary search achieves logarithmic time when the data is sorted, and why it is notoriously easy to get wrong.
  • When it pays off to sort the data first in order to search faster.

Sequential Search​

The most direct strategy inspects the elements one by one, from the first to the last, until it finds the value or runs out of elements. It works on any sequence, sorted or not.

public static boolean search(int[] list, int value) {
    int i = 0;
    int n = list.length;
    while ((i < n) && (list[i] != value))
        i++;
    if (i == n)
        return false;     // we went past the last element: not found
    else
        return true;      // we stopped at position i: found
}

The while condition contains two comparisons. The first one, i < n, protects the array: thanks to the short-circuit evaluation of &&, list[i] is only accessed when i is a valid position. When i reaches n, the second comparison is not evaluated.

We count each elementary instruction as one unit of time. The cost depends on where the value is, so we analyze the three cases.

Sequential Search with a Sentinel​

Look again at the loop of the sequential search: in every iteration it checks two conditions, i < n and list[i] != value. The first one is only needed to avoid running past the end of the array. Can we get rid of it?

The sentinel technique does exactly that: before searching, we add the value we are looking for at the end of the sequence. Now the loop is guaranteed to find it, either in its original position or in the extra position, so the bounds check is no longer necessary.

public static boolean search(List<Integer> list, int value) {
    list.add(value);                    // the sentinel: now the value is surely in the list
    int i = 0;
    while (list.get(i) != value)
        i++;
    if (i == list.size() - 1)           // we stopped at the sentinel
        return false;
    else
        return true;
}

What have we gained?​

The complexity is still O(n)O(n)O(n) in the worst and average cases: the sentinel does not change the complexity class. What changes is the constant: about 2n2n2n operations instead of 3n3n3n, so we expect the sentinel version to need roughly two thirds of the time.

Measurements confirm it, with an important nuance. Searching for a missing value in an array of a million integers, the sentinel version took about 60-70 % of the time of the standard version when running without optimization (-Xint), just as the operation count predicts. With the JIT compiler enabled, the difference became small and irregular: the optimizer already makes the bounds check very cheap. Micro-optimizations that reduce the constant are real, but their effect depends heavily on the environment, and they never compensate for a worse complexity.

The price of the sentinel
  • It modifies the input. The version above leaves the sentinel at the end of the list. A correct implementation must remove it before returning (one more operation), and it is not safe if other threads are reading the list at the same time.
  • It needs a free position. With a plain array, there must be space for one more element. With an ArrayList, adding at the end is cheap (amortised constant time), but with other implementations it may not be.
  • Beware of get(i) on linked lists. If the list were a LinkedList, each get(i) would traverse the list from the beginning, making the search quadratic! The analysis assumes constant-time access by position.

Binary (Dichotomous) Search​

Sequential search is the best we can do when the data has no particular order: every element could be the one we are looking for, so in the worst case we must inspect all of them (Ω(n)\Omega(n)Ω(n)). But if the array is sorted, a single comparison tells us much more.

Compare the value with the central element:

  • if they are equal, we have found it;
  • if the value is greater, it can only be in the right half, so we discard the left half;
  • if it is smaller, it can only be in the left half.

Each comparison halves the search space. It is the strategy we use when looking up a word in a paper dictionary.

public static boolean search(int[] list, int value) {     // precondition: list is sorted
    int left = 0;
    int right = list.length - 1;
    while (left <= right) {
        int k = left + (right - left) / 2;                 // central position
        if (list[k] == value)
            return true;
        if (value > list[k])
            left = k + 1;                                  // discard the left half
        else
            right = k - 1;                                 // discard the right half
    }
    return false;                                          // empty interval: not found
}

The variables left and right delimit the part of the array where the value can still be. The loop continues while that interval is non-empty (left <= right).

Analysis​

  • 🔴 Worst case
  • 🟡 Average case

The value is in the central position of the whole array, and it is found in the first iteration:

Tbest(n)=2⏟left, right+1⏟condition+1⏟k+1⏟==+1⏟return=6  ∈  O(1)T_{best}(n) = \underbrace{2}_{\text{left, right}} + \underbrace{1}_{\text{condition}} + \underbrace{1}_{k} + \underbrace{1}_{==} + \underbrace{1}_{\text{return}} = 6 \;\in\; O(1)Tbest​(n)=left, right2​​+condition1​​+k1​​+==1​​+return1​​=6∈O(1)

The value is not in the array. Each iteration costs a constant number of operations: the loop condition, the calculation of k, two comparisons and one assignment, that is, 5 operations. The question is how many iterations there are.

The size of the interval goes n→n2→n4→⋯→1→0n \to \frac{n}{2} \to \frac{n}{4} \to \cdots \to 1 \to 0n→2n​→4n​→⋯→1→0. The number of times we can halve nnn before reaching an empty interval is ⌊log⁡2n⌋+1\lfloor \log_2 n \rfloor + 1⌊log2​n⌋+1. Therefore:

Tworst(n)≈5(⌊log⁡2n⌋+1)+4  ∈  O(log⁡n)T_{worst}(n) \approx 5 (\lfloor \log_2 n \rfloor + 1) + 4 \;\in\; O(\log n)Tworst​(n)≈5(⌊log2​n⌋+1)+4∈O(logn)

(the final +4+4+4 accounts for the initializations, the last evaluation of the condition and the return). For n=1,000n = 1{,}000n=1,000 the loop runs at most 10 times, and for n=1,000,000n = 1{,}000{,}000n=1,000,000 at most 20 times, as we checked by instrumenting the code.

A detailed analysis, assuming that the value is present and equally likely to be in any position, shows that binary search needs about log⁡2n−1\log_2 n - 1log2​n−1 iterations on average: only one iteration less than in the worst case. This is because half of the positions are only reached in the last iteration, a quarter in the one before, and so on. The average case is therefore also O(log⁡n)O(\log n)O(logn).

The scale of O(log n)

For an array of one billion elements, sequential search may need a billion comparisons. Binary search needs at most 30 iterations (230≈1.07×1092^{30} \approx 1.07 \times 10^9230≈1.07×109). Doubling the size of the array adds just one more iteration.

Binary search is easy to get wrong​

Binary search is famous for being simple to describe and surprisingly hard to implement correctly. Small changes in the conditions break it. Consider this variant, which looks reasonable:

int left = 0, right = list.length - 1, k;
do {
    k = (left + right) / 2;
    if (value > list[k]) left = k + 1;
    else right = k - 1;
} while ((list[k] != value) && (left < right));    // BUG
return list[k] == value;
🧠 Checkpoint: Find the bug

Question: Trace this variant searching for 3 in [1, 2, 3]. What does it return?

Answer: It returns false, although 3 is in the array. In the first iteration, k=1k = 1k=1 and 3>23 \gt 23>2, so left = 2. Now left and right are both 2: the interval still contains one candidate (position 2), but the condition left < right is false and the loop stops without examining it. The function then checks list[1], which is 2, and reports that the value is not present.

We ran a stress test (as in the case study) comparing this variant with the correct version on 20,000 random sorted arrays, always searching for values that were present: the variant failed in about 45 % of the searches. The correct condition is left <= right (the interval is non-empty), and the element at the central position must be compared with the value in the same iteration in which it is computed.

Two more details of the correct version deserve attention:

  • The central position is computed as left + (right - left) / 2 instead of (left + right) / 2. Both are mathematically equivalent, but with very large arrays the sum left + right can exceed the maximum int value and overflow, producing a negative index. This bug was present for years in the binary search of widely used libraries, including Java's own.
  • The loop invariant. At the start of every iteration, if the value is in the array, it is between positions left and right. Checking that each branch preserves this invariant, and that the interval shrinks in every iteration, is the way to convince yourself that the algorithm is correct and terminates.

Is it worth sorting the data first?​

Binary search needs sorted data, and sorting has a cost: about nlog⁡nn \log nnlogn operations with a good algorithm, as you will see in the next chapter. Whether it pays off depends on how many searches we will perform on the same data.

  • To perform mmm searches with sequential search, we need about m⋅nm \cdot nm⋅n operations in the worst case.
  • To sort once and then perform mmm binary searches, we need about nlog⁡n+mlog⁡nn \log n + m \log nnlogn+mlogn operations.

If we search only once or twice, sorting first is not worth it: sorting alone is already more expensive than one sequential search. But as soon as the number of searches mmm is larger than about log⁡n\log nlogn (around 20 for a million elements), sorting first and using binary search wins, and the advantage grows with every additional search. This kind of reasoning, which weighs a one-time cost against the cost of repeated operations, is very common in algorithm and system design (for example, when deciding whether to create an index in a database).

🧠 Checkpoint: Why not always binary search?

Question: Give three situations in which sequential search is a better choice than binary search.

Answer: (1) The data is not sorted and we only need to search a few times, so sorting would cost more than searching. (2) The data is stored in a structure without direct access by position, such as a linked list, where reaching the central element already takes linear time. (3) The collection is very small (a few dozen elements), where the simpler loop may be faster in practice because of its lower constants. A fourth one: the data changes constantly, and keeping it sorted after every insertion would be too expensive.

Looking Ahead: Sorting​

Binary search showed us how much sorted data is worth. The next chapter focuses on sorting algorithms, and analyzes them with all the tools of this chapter. Besides their time complexity in the best, worst and average cases, three properties will be important:

  1. Space (in place or not): does the algorithm reorganize the elements inside the original array, using only a constant amount of extra memory, or does it need auxiliary arrays proportional to nnn?
  2. Stability: if two elements have the same key (for example, two students with the same grade), does the algorithm preserve their original relative order? This matters when sorting by several criteria in successive passes.
  3. Adaptivity: does the algorithm take advantage of data that is already partially sorted, finishing faster, or does it perform the same work regardless of the input?
Common mistakes
  • Binary search on unsorted data. It returns wrong answers silently; it needs sorted data with direct access.
  • Writing while (left < right) or comparing the central element in a later iteration. Use left <= right and compare the central element in the same iteration.
  • Computing the middle as (left + right) / 2. It can overflow for large indices; use left + (right - left) / 2.
  • Sorting before a single search. Sorting only pays off when there are many searches.

  • Sequential search works on any sequence.   • The sentinel removes the bounds check and reduces the worst case to 2n+52n + 52n+5: a better constant, the same complexity, and some practical costs (modifying the input, needing space).

  • Sorting first pays off when the number of searches is large enough compared with log⁡n\log nlogn.
