# Exercises: Sorting

These exercises review the whole sorting chapter. They use the versions of the algorithms given in the lessons (for example, the bubble sort of the lesson moves the **smallest** elements to the **left**, scanning from right to left). Try each exercise before reading its solution: the solutions are grouped at the [end of the page](#solutions).

## Solutions

<span id="sol-2-1"></span>**2.1.** A method that writes zeros in every position, or simply returns `[1, 2, ..., n]`, passes the test. A correct test must also check that the output is a **permutation** of the input: the same elements, the same number of times. A simple way is to sort a copy with a trusted method (`Arrays.sort`) and compare the arrays; another is to compare the frequency of each value before and after.

<ToStatement n="2.1" />

<span id="sol-2-2"></span>**2.2.** Stable: bubble sort, insertion sort and Mergesort (when, in the merge, equal elements are taken from the **left** half first). Unstable: selection sort, Quicksort and Heapsort. Example for selection sort: `2a 2b 1`. The first step swaps the minimum `1` with the element in position 0, `2a`, giving `1 2b 2a`: the two 2s have changed their relative order.

<ToStatement n="2.2" />

<span id="sol-2-3"></span>**2.3.** By **name first**, then by **grade**. The second sort decides the main order (grade). Because it is stable, students with the same grade keep the order they had after the first sort, which was alphabetical. Sorting in the other order would leave the list sorted by name, with grades mixed. This is how spreadsheets and many databases sort by several columns.

<ToStatement n="2.3" />

<span id="sol-2-4"></span>**2.4.** The inversions are the pairs out of order: (4,1), (4,2), (7,1), (7,6), (7,2), (6,2), so **6 inversions**. Every swap of adjacent elements removes exactly one inversion, so bubble sort performs **6 swaps**, and insertion sort performs **6 shifts**. Running the bubble sort with sentinel on this array confirms it: 6 swaps, in 4 passes and 10 comparisons.

<ToStatement n="2.4" />

<span id="sol-2-5"></span>**2.5.** `2 3 4 5 6 1` needs **2 passes**: in the first one, the `1` travels all the way from the end to the front, and the second pass finds nothing to swap. `6 1 2 3 4 5` needs **5 passes** (with 15 comparisons), the maximum for $n = 6$: the `6` can only move **one** position to the right per pass, because each pass carries small elements to the left. For this version of the algorithm, the turtles are **large elements near the beginning**; the rabbits are small elements near the end. (The version that scans from left to right has the opposite behavior. Bidirectional bubble sort alternates both directions to move both kinds quickly.)

<ToStatement n="2.5" />

<span id="sol-2-6"></span>**2.6.** Each comparison `key < elements[j]` either succeeds, and then `key` passes over an element larger than itself (removing one inversion), or fails, and then the insertion of that key ends. So there are exactly $I$ successful comparisons plus at most one failed comparison for each of the $n - 1$ insertions: between $I$ and $I + n - 1$ comparisons. (On random arrays of 20 elements we counted, for example, 103 comparisons with $I = 87$, inside the range 87 to 106.) If every element is at most $d$ positions away from its final place, an element $y$ that is larger than $x$ and stands to its left must be among the $2d - 1$ positions just before $x$ (otherwise one of the two would be more than $d$ positions away from its place). So each element forms fewer than $2d$ inversions with the elements to its left, $I \lt 2dn$, and the cost is $O(n \cdot d)$: **linear** for constant $d$. This is why insertion sort is used for nearly sorted data.

<ToStatement n="2.6" />

<span id="sol-2-7"></span>**2.7.** $\lfloor n/2 \rfloor$ swaps: 3 for $n = 6$ and also 3 for $n = 7$. The first step swaps the first and last elements (`n` and `1`), which puts **both** in their final positions. The same happens with the second and the next-to-last, and so on, so after $\lfloor n/2 \rfloor$ swaps every remaining minimum is already in place and the algorithm (which skips the swap when `i == posMin`) swaps nothing else.

<ToStatement n="2.7" />

<span id="sol-2-8"></span>**2.8.** Recurse only on the **smaller** part and handle the larger part with a loop:

```java
private void quickSortIterative(int[] elements, int left, int right) {
    while (right - left >= 3) {
        int p = partition(elements, left, right);   // the partition of the lesson
        if (p - left < right - p) {                 // left part is smaller
            quickSortIterative(elements, left, p - 1);
            left = p + 1;                           // continue with the right part
        } else {
            quickSortIterative(elements, p + 1, right);
            right = p - 1;                          // continue with the left part
        }
    }
    sortSmall(elements, left, right);               // 3 elements or fewer
}
```

Here `partition` is the partition loop of the lesson, moved to a method that returns the final position of the pivot, and `sortSmall` is the `medianOfThree` call, which already sorts ranges of 3 elements or fewer. Every recursive call receives at most half of the current range, so there can be at most $\log_2 n$ nested calls. The **time** in the worst case is still $O(n^2)$; only the memory is protected.

<ToStatement n="2.8" />

<span id="sol-2-9"></span>**2.9.**
- (a) An array that is already sorted (or in reverse order): every partition leaves one part empty.
- (b) There are inputs that defeat it, but they are not "natural": they must be built on purpose, placing the smallest (or largest) remaining element in the center of each subarray. Sorted and reversed arrays, which defeat (a), are the **best** case for (b).
- (c) No fixed input is bad for a random pivot. The **expected** time is $O(n \log n)$ for every input; quadratic time is possible only through extremely unlikely random choices. This is the main argument for randomized pivots: they protect against inputs crafted by an adversary.

<ToStatement n="2.9" />

<span id="sol-2-10"></span>**2.10.** $n = 6$, so `downHeap` runs on positions 2, 1 and 0:
- Position 2 (`2`): its only child is `5` (position 5). Swap: `3 9 5 1 4 2`.
- Position 1 (`9`): its children are `1` and `4`; `9` is larger. No change.
- Position 0 (`3`): its children are `9` and `5`; swap with `9`: `9 3 5 1 4 2`. Continue at position 1 (`3`): children `1` and `4`; swap with `4`: `9 4 5 1 3 2`.

Result: **`9 4 5 1 3 2`**. Each parent is greater than or equal to its children.

<ToStatement n="2.10" />

<span id="sol-2-11"></span>**2.11.** Each comparison places one element in the output, and the merge stops comparing when one of the lists is empty. *Best case*: every element of the shorter list is smaller than every element of the longer one, $\min(m, k)$ comparisons; for example `1 2 3` and `4 5 6 7` need **3**. *Worst case*: both lists are exhausted at the very end, $m + k - 1$ comparisons; for example `2 4 6` and `1 3 5 7` need **6**.

<ToStatement n="2.11" />

<span id="sol-2-12"></span>**2.12.** Put the first element of each list in a **min-heap** (a `PriorityQueue`), together with the index of its list. Repeatedly extract the minimum, append it to the output, and insert the next element from the same list. The heap never has more than $k$ elements, so each of the $N$ extractions and insertions costs $O(\log k)$: $O(N \log k)$ in total. Merging the lists two by two in a balanced way (as Mergesort does) gives the same bound.

<ToStatement n="2.12" />

<span id="sol-2-13"></span>**2.13.** A **min-heap of size 10**. For each new number, if the heap has fewer than 10 elements, insert it; otherwise, if the number is larger than the minimum of the heap (its root), replace the root and restore the heap. At the end, the heap holds the 10 largest. Each step costs $O(\log k)$ with $k = 10$, so the total is $O(n \log k)$, practically linear, with $O(k)$ memory.

<ToStatement n="2.13" />

<span id="sol-2-14"></span>**2.14.** There are $5! = 120$ possible orders, and each comparison has two outcomes, so at least $\lceil \log_2 120 \rceil = 7$ comparisons are needed in the worst case. The bound is achievable: there is an algorithm (merge insertion, by Ford and Johnson) that sorts any 5 elements with exactly 7 comparisons. Mergesort needs 8 in its worst case for $n = 5$.

<ToStatement n="2.14" />

<span id="sol-2-15"></span>**2.15.**
- (a) **Counting sort**: an array of 121 counters, one pass to count and one to write the result. $O(n + k)$ with $k = 121$: linear, and much faster than any comparison sort for 47 million elements.
- (b) **Radix sort** with base $256 = 2^8$: four passes of counting sort, one per byte of the 32-bit integers, each $O(n + 256)$. In total, $O(4 (n + 256)) = O(n)$. (Negative numbers need care: the most significant byte must be treated with the sign bit inverted.)

<ToStatement n="2.15" />

<span id="sol-2-16"></span>**2.16.**
- (a) **Insertion sort**, or the library's **TimSort** (`Arrays.sort` for objects, `List.sort`), which detects sorted runs. Both are close to linear when few elements are out of place.
- (b) **Heapsort**: $O(n \log n)$ in every case and $O(1)$ additional memory.
- (c) A **stable** algorithm: Mergesort, or the library's TimSort, which is stable. Quicksort and Heapsort would not respect the previous order.
- (d) **External sorting**: sort the data in chunks of about 16 GB in memory, write each sorted chunk to disk, and merge the chunks with a $k$-way merge (exercise 2.12), reading and writing the disk sequentially.

<ToStatement n="2.16" />
