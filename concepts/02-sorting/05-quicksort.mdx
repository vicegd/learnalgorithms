# Quicksort

Quicksort, invented by Tony Hoare around 1960, is one of the most important algorithms ever designed. It is the basis of the sorting routines of many programming languages and libraries, and it is usually the fastest general-purpose sorting algorithm in practice. It improves the idea of **exchange**: instead of exchanging adjacent elements, it exchanges elements that are far apart, removing many inversions at once.

Quicksort is also our first example of a **recursive** algorithm based on **divide and conquer**, a paradigm that you will study in depth later in the course.

:::note What you will learn in this lesson
- The idea of **partitioning** around a pivot, and why it leads to a recursive algorithm.

- Why Quicksort is $O(n \log n)$ in the best and average cases but $O(n^2)$ in the worst case.
- Its practical weaknesses (recursion depth, repeated keys, small subarrays) and how professional implementations address them.
:::

## The Idea: Partitioning

Quicksort is based on **partitioning**. Choose an element of the vector, called the **pivot**, and rearrange the vector so that:

- all the elements **smaller** than the pivot are on its **left**;
- all the elements **greater** than the pivot are on its **right**;
- the pivot is between them.

After partitioning, the pivot is in its **final position**: it will not move again. And the two parts on each side can be sorted **independently**, because no element will ever need to cross from one side to the other. So we apply the same idea to each part, recursively, until the parts have one element (or none), which are trivially sorted.

```
                 2  3  1 [4] 7  6           partition around 4
                /                \
         1 [2] 3                   [6] 7    partition each part
        /       \                  
      [1]       [3]                   [7]  
```

The sequence of partitions forms a **tree**. If each pivot divides its part into two halves of similar size, the tree is balanced and has about $\log_2 n$ levels. If the pivot is always at one end of its part (the smallest or the largest element), one of the parts is empty and the "tree" degenerates into a **list** of $n$ levels. This is the key to the efficiency of Quicksort, as we will see in the analysis: **the choice of the pivot is crucial**.

---

## Choosing the Pivot

The ideal pivot is the **median** of the elements (the element that would be in the middle if they were sorted), because it divides the part into two halves of equal size. The options are:

| Criterion | Assessment |
| :--- | :--- |
| **The median** | The ideal solution, but it is very expensive to compute exactly. |
| **The first element** | "Cheap", but a bad choice: on data that is already sorted (very common in practice), it is always the smallest element, and every partition is completely unbalanced. |
| **The last element** | Same problem as the first one. |
| **A random element** | Statistically, it is not a bad choice: no particular input is consistently bad. It has the cost of generating random numbers. |
| **The central element** | Statistically not a bad choice, and it works very well on sorted or reverse-sorted data. |
| **Median-of-three** | A compromise: take three elements (the first, the last and the central one), and use their median as the pivot. It does not guarantee anything, but it is a good indicator of the real median at a very low cost. |

The course implementation uses the **median-of-three**. It **sorts** the three elements among themselves (so the smallest ends up at the left end and the largest at the right end) and returns the position of the central one, which holds their median:

```java
private int medianOfThree(int[] elements, int left, int right) {
    int center = left + (right - left) / 2;
    if (elements[left] > elements[center]) Util.swap(elements, left, center);
    if (elements[left] > elements[right]) Util.swap(elements, left, right);
    if (elements[center] > elements[right]) Util.swap(elements, center, right);
    return center;                    // elements[left] <= elements[center] <= elements[right]
}
```

A useful side effect: if the part has **three elements or fewer**, the median-of-three has already sorted it completely, and the recursion can stop there.

## The Partitioning Strategy

Once the pivot is chosen, the partition is done in place with two indices that move towards each other:

1. **Hide the pivot**: exchange it with the last element, so that it does not get in the way.
2. Move `i` from the left until it finds an element **greater** than the pivot (an element that should be on the right).
3. Move `j` from the right until it finds an element **smaller** than the pivot (an element that should be on the left).
4. If `i` and `j` have not crossed, **exchange** those two elements: each one goes to its correct side.
5. Repeat steps 2 to 4 until `i` and `j` cross. Then `i` marks the first position of the right part: **place the pivot** there by exchanging it with the last element.

```java
private void quickSortRecursive(int[] elements, int left, int right) {
    if (left >= right) return;                         // 0 or 1 elements: sorted
    int center = medianOfThree(elements, left, right);
    if ((right - left) >= 3) {                         // with 3 elements or fewer, already sorted
        int pivot = elements[center];
        Util.swap(elements, center, right);            // hide the pivot at the end
        int i = left;
        int j = right - 1;
        do {
            while (elements[i] <= pivot && i < right) i++;   // first element > pivot
            while (elements[j] >= pivot && j > left) j--;    // first element < pivot
            if (i < j) Util.swap(elements, i, j);
        } while (i < j);
        Util.swap(elements, i, right);                 // place the pivot in its final position
        quickSortRecursive(elements, left, i - 1);     // sort the left part
        quickSortRecursive(elements, i + 1, right);    // sort the right part
    }
}

public void sort(int[] elements) {
    quickSortRecursive(elements, 0, elements.length - 1);
}
```

## Analysis

Partitioning a part of $m$ elements costs $O(m)$: each element is compared with the pivot about once, as `i` and `j` sweep the part. The total cost therefore depends on how **balanced** the partitions are.

<Tabs>
<TabItem value="best" label="🟢 Best case" default>

The pivot always divides the part into **two halves**. The tree of partitions has $\log_2 n$ levels, and at each level, the parts together contain at most $n$ elements, so each level costs $O(n)$:

$$
T(n) = 2\,T\!\left(\frac{n}{2}\right) + O(n) \quad\Longrightarrow\quad T(n) \in O(n \log n)
$$

(You will learn to solve this kind of equation, called a **recurrence**, in the divide and conquer chapter.)

</TabItem>
<TabItem value="worst" label="🔴 Worst case">

The pivot is always the **smallest** (or largest) element of its part, so one of the parts is empty and the other one has $m - 1$ elements. The tree has $n$ levels, with parts of sizes $n, n-1, n-2, \dots$:

$$
T(n) = T(n-1) + O(n) \quad\Longrightarrow\quad T(n) \in O(n^2)
$$

The total number of comparisons is about $n + (n-1) + \cdots + 1 \approx \frac{n^2}{2}$, as bad as the simple algorithms. With the **first element** as pivot, this happens precisely when the data is **already sorted** (or reverse-sorted). With median-of-three it is much harder to trigger, but specially constructed inputs can still cause it.

</TabItem>
<TabItem value="average" label="🟡 Average case">

When the pivot is chosen at random (or the input is random), partitions are not perfectly balanced, but they are "reasonably" balanced most of the time. A detailed analysis shows that the average number of comparisons is about $2n \ln n \approx 1.39\, n \log_2 n$: only about 39 % more than the best case. The average case is **$O(n \log n)$**.

</TabItem>
</Tabs>

We checked the effect of the pivot by counting comparisons with $n = 1{,}000$ (the theoretical value of $n \log_2 n$ is about 9,966):

| Pivot | Sorted | Random | Reverse |
| :--- | ---: | ---: | ---: |
| Median-of-three | 9,541 comparisons, depth 9 | 15,370 comparisons, depth 18 | 10,539 comparisons, depth 9 |
| First element | **499,500** comparisons, depth **999** | 12,563 comparisons, depth 25 | **499,500** comparisons, depth **999** |

With the first element as pivot, sorted and reverse inputs trigger the worst case: exactly $\frac{n(n-1)}{2}$ comparisons and a recursion as deep as the array is long. With median-of-three, the same inputs are actually the **easiest** ones.

### Properties

| Property | Quicksort |
| :--- | :--- |
| Best case | $O(n \log n)$ |
| Average case | $O(n \log n)$ |
| Worst case | $O(n^2)$ |
| Extra memory | The recursion stack: $O(\log n)$ in the best and average cases, $O(n)$ in the worst case |
| Stable | **No**: partitioning exchanges distant elements |
| Adaptive | Not in general |

In practice, Quicksort is **very fast for $n \gt 20$**: its inner loops are very simple and it accesses memory sequentially, which modern processors handle very efficiently. For very small parts, simple algorithms are faster.

## Practical Weaknesses and Improvements

### Recursion depth

In the worst case, the recursion reaches a depth of $n$, which can exhaust the call stack. The standard fix is to **recurse only on the smaller part** and handle the larger part with a loop. Since the smaller part has at most half the elements, the depth is then at most $\log_2 n$, whatever the pivots.

### Many repeated keys

Look at the scanning loops: `i` advances while `elements[i] <= pivot`, and `j` retreats while `elements[j] >= pivot`. If **all the elements are equal**, `i` runs to the end of the part, the pivot is placed at the last position, and every partition is completely unbalanced: **quadratic** time. We measured it with the course implementation: sorting 20,000 equal elements took about 97 ms (and 25 ms for 10,000: the time quadruples when $n$ doubles), versus about 2 ms for 20,000 random elements. With 50,000 equal elements, the recursion is so deep that it ends with a `StackOverflowError`.

Arrays with many repeated keys are very common (sorting people by age, or orders by status). Two well-known solutions:

- stop **both** scans at elements **equal** to the pivot (`<` and `>` instead of `<=` and `>=`) and exchange them; this splits runs of equal keys evenly between both sides;
- use a **three-way partition** (the "Dutch national flag" problem, studied by Dijkstra), which divides the part into elements **smaller than**, **equal to** and **greater than** the pivot, and recurses only on the first and last groups. With many equal keys, it becomes much faster than standard Quicksort.

### Small parts

For parts of fewer than about 10 to 20 elements, the overhead of recursion outweighs its benefits. Many implementations stop the recursion at that size and finish with **insertion sort**, which is very fast on small and almost sorted arrays (the parts are already roughly in their final zones).

### Guaranteeing $O(n \log n)$

Even with a good pivot strategy, an adversary can construct inputs that make Quicksort quadratic. **Introsort** monitors the recursion depth and, if it exceeds a multiple of $\log n$, switches to Heapsort, which guarantees $O(n \log n)$. It is used in several standard libraries. Java's `Arrays.sort` for primitive types uses a highly tuned **dual-pivot Quicksort**, which partitions into three parts using two pivots.

### Parallelism

After a partition, the two parts are completely **independent**, so they can be sorted **in parallel** by different threads. This makes Quicksort a natural candidate for the parallel algorithms chapter.

  **Question:** A program sorts, every night, a list of transactions that is usually already sorted except for a few hundred new transactions appended at the end. Which pivot strategy would you avoid? Is Quicksort even the best choice here?

  **Answer:** Avoid the **first** or **last** element: on almost sorted data, they produce extremely unbalanced partitions, with quadratic time and a risk of stack overflow. Median-of-three or the central element work well. But for almost sorted data, an **adaptive** algorithm is better still: insertion sort (if there are very few misplaced elements) or an algorithm that detects sorted runs, such as Mergesort-based TimSort, which Java uses for objects.

For $n = 8{,}000$ random elements, Quicksort takes about **4 ms**, while insertion sort takes 329 ms and bubble sort more than a second. And the gap grows with $n$: doubling the size roughly doubles the time of Quicksort (a little more, because of the $\log n$ factor), while it quadruples the time of the simple algorithms.

## Summary

- Quicksort **partitions** the vector around a **pivot**, which ends in its final position, and sorts both parts recursively.
- The pivot choice is crucial: the first or last element is cheap but disastrous on sorted data; **median-of-three** is a good compromise; a random pivot makes the expected cost $O(n \log n)$ for every input.
- Best and average cases: $O(n \log n)$. Worst case: $O(n^2)$. It is in place (apart from the recursion stack) but **not stable**.
- Practical improvements: recurse on the smaller part (stack depth $O(\log n)$), handle repeated keys (three-way partition), switch to insertion sort for small parts, and fall back to Heapsort to guarantee $O(n \log n)$ (Introsort).
