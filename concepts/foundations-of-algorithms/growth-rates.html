Growth Rates: What Complexity Means in Practice

Asymptotic notation gives us a precise language. This lesson turns it into practical intuition: what the most common complexity classes mean in real time, how to predict the time an algorithm will need for a larger input, how to estimate the largest input it can handle in a given time, and why no improvement in hardware can change the complexity of an algorithm.

Asymptotic analysis allows us:

  • to measure the inherent difficulty of a problem;
  • to estimate the time and space required by an algorithm before running it;
  • to compare algorithms that solve the same problem in terms of efficiency.
What you will learn in this lesson
  • The main complexity classes, from O(1)O(1)O(1) to O(nn)O(n^n)O(nn), and which ones are acceptable in practice.
  • How dramatically the classes differ when nnn grows, and where the "small nnn" exceptions are.
  • How to calculate the expected execution time for a new problem size, and the largest problem size solvable in a given time.
  • The principle of invariance and its consequences.

The classes up to O(nk)O(n^k)O(nk) are polynomial; from O(2n)O(2^n)O(2n) onwards they are not polynomial. This border is very significant in computer science: problems that can be solved in polynomial time are usually considered tractable, while those that seem to require exponential time are considered intractable for large inputs. Some of the most famous open questions in computer science (such as whether P equals NP) are about exactly this border. Several design techniques of this course, such as backtracking and branch and bound, exist precisely to deal with problems for which no polynomial algorithm is known, trying to avoid exploring the whole exponential search space.

Predicting the Largest Solvable Problem​

Question: An O(n2)O(n^2)O(n2) program processes 5,000 records per night. The company buys a server 16 times faster. How many records can it process per night now? And if the program were O(2n)O(2^n)O(2n) and processed 40 records?

The Principle of Invariance​

Given an algorithm of complexity O(f(n))O(f(n))O(f(n)), it will always have that complexity, regardless of the language in which it is programmed, the quality of the compiler, the speed of the computer, etc. These factors affect the implementation constant, but never the complexity O(f(n))O(f(n))O(f(n)).

More formally: two different implementations of the same algorithm, on any two machines, will never differ in efficiency by more than a constant factor. If one takes t1(n)t_1(n)t1​(n) and the other t2(n)t_2(n)t2​(n), there is a constant ccc such that t1(n)≤c⋅t2(n)t_1(n) \le c \cdot t_2(n)t1​(n)≤c⋅t2​(n) for large enough nnn.

This principle has three important consequences:

  1. It justifies the asymptotic approach. Since languages, compilers and machines only change the constant, studying the order of growth tells us something true about the algorithm itself, valid on any computer, present or future.
  2. It explains the time ratios of the lab. When we compare the same algorithm in two environments (for example, Python and Java), the ratio of their times tends to a constant: the implementation constant.
  3. It sets the limits of hardware. Better hardware divides the time by a constant. As the previous tables show, that can compensate for a better algorithm only for small inputs: for large inputs, the algorithm with the better growth rate always wins.

Summary​

  • The common complexity classes are, from best to worst: O(1)O(1)O(1), O(log⁡n)O(\log n)O(logn), O(n)O(n)O(n), O(nlog⁡n)O(n \log n)O(nlogn), O(n2)O(n^2)O(n2), O(n3)O(n^3)O(n3), O(nk)O(n^k)O(nk), O(2n)O(2^n)O(2n), O(n!)O(n!)O(n!) and O(nn)O(n^n)O(nn). Polynomial classes are considered tractable; exponential ones are not.
  • With about 10910^9109 operations per second, a quadratic algorithm handles tens of thousands of elements per second, an exponential one only a few dozen.
  • To predict times: t2=f(n2)f(n1)⋅t1t_2 = \frac{f(n_2)}{f(n_1)} \cdot t_1t2​=f(n1​)f(n2​)​⋅t1​. To predict sizes: n2=f−1(t2t1⋅f(n1))n_2 = f^{-1}\left(\frac{t_2}{t_1} \cdot f(n_1)\right)n2​=f−1(t1​t2​​⋅f(n1​)).
  • For exponential algorithms, more time or faster hardware only adds a constant to the solvable size.
  • The principle of invariance: implementation, language and hardware change only the constant, never the complexity.
