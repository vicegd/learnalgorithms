# Concurrency and Parallelism

Until now, every algorithm in this course has been **sequential**: one instruction after another, on a single processor. But the computers we use, from phones to servers, have several processor **cores**, and a sequential program uses only one of them. **Parallel algorithms** divide the work so that several cores can do it at the same time.

This chapter connects directly with divide and conquer: if a problem can be divided into **independent** subproblems, those subproblems can be solved **simultaneously**. This first lesson introduces the basic concepts; the next ones present Java's Fork/Join framework and how to analyze the performance of parallel algorithms.

:::note What you will learn in this chapter
- Why processors have several cores, and why that matters for software.
- The difference between **concurrency** and **parallelism**, and the roles of processes, threads and tasks.
- The **Fork/Join** framework of Java, and how to turn a divide and conquer algorithm into a parallel one.
- How to choose the **threshold** below which the work is done sequentially.
- How to measure and predict the benefit of parallelism: **speedup**, **efficiency** and **Amdahl's law**.
:::

## Why Do We Have Multi-core Processors?

For decades, the performance of processors grew exponentially, thanks to two factors: the number of transistors on a chip doubled about every two years (an observation known as **Moore's law**, after Gordon Moore), and the **clock frequency** kept increasing. Programs became faster without any change: you just had to wait for the next generation of processors.

Around the turn of the century, this approach hit a wall. As frequencies increased, so did the **power consumption** and the **heat** produced by the chips, to levels that could not be dissipated. Designers needed another way to keep increasing performance.

The answer was to place **several processors (cores) on the same chip**, working in parallel, like a job broken down into smaller tasks and distributed among a group of people. Multi-core processors reached the market in the mid-2000s. Today, consumer processors have from a few cores to a few dozen, servers many more, and graphics processors (GPUs) thousands of simple cores.

But multiple cores are not enough: **applications must be designed to use them**. A sequential program runs on a single core, no matter how many the computer has. That is why parallel algorithms have become an essential part of software engineering.

## Concurrent Computing

**Concurrent computing** consists of performing **two or more tasks** whose executions overlap in time, on **one or more** processors. It is the opposite of sequential computing, in which a task starts only when the previous one has finished.

Concurrency is extremely common in everyday programs:

- while an application waits for the user to enter a value, it may be saving other data in a database;
- many tasks are performed **in the background**: downloading updates, indexing files, synchronising with the cloud;
- a web server attends many clients at the same time.

Concurrent tasks do **not** necessarily run at the same physical instant. With a **single** processor, the operating system alternates between them very quickly, giving the **feeling** of simultaneity, while the instructions are actually executed one after another. In Java, the basic tool to create concurrent units of execution is the class `Thread`.

## Parallel Computing

**Parallel computing** performs several tasks **at the same time**, using **more than one processor**. It is therefore intrinsically concurrent (multithreaded), but with real simultaneity.

| | Concurrency | Parallelism |
| :--- | :--- | :--- |
| Idea | Dealing with several tasks at once | Doing several tasks at once |
| Processors | One or more | More than one |
| Main goal | Structure and responsiveness (do not block while waiting) | Speed (finish the work sooner) |
| Example | A text editor that checks spelling while you type | Sorting a huge array using all the cores |

</Figure>

Parallelism can greatly speed up many operations, such as sorting, searching or transforming data. It is especially well suited to any task that can be broken down into **smaller, independent components**, which is exactly what **divide and conquer** does.

:::tip Concurrency is not parallelism
Rob Pike, one of the creators of the Go language, summarized the difference in a famous talk: *concurrency is about **dealing** with lots of things at once; parallelism is about **doing** lots of things at once*. Concurrency is a way of structuring a program; parallelism is a way of executing it. You can watch the talk [Concurrency is not parallelism](https://www.youtube.com/watch?v=cN_DpYBzKso).
:::

## Processes, Threads and Tasks

Concurrency is built on three nested mechanisms:

- A **process** is an operating system abstraction that allows a computer to support different units of execution. Each process has its own memory space; for example, each running application is usually a separate process.
- A **thread** belongs to exactly one process and is a sequence of instructions that is executed independently of the others. The threads of a process **share its resources**, in particular its memory, which makes communication between them easy (and dangerous).
- A **task** is a small unit of work: a component of the solution that some thread has to execute.

<Figure caption="Processes have separate memory; the threads of a process share its memory, and each thread executes tasks.">
  <FigProcessesThreadsTasks />
</Figure>

The **operating system** decides which threads run on which processors, and when: concurrently (alternating on the same core) or in parallel (on different cores).

### The danger of sharing

Because threads share memory, they must be **synchronised** so that they do not interfere with each other. Two classic problems:

- **Race conditions:** two threads modify the same data at the same time, and the result depends on the exact order of their instructions. For example, if two threads execute `counter++` simultaneously, one of the increments may be lost, because each one reads the old value before the other writes the new one.
- **Deadlocks:** threads block each other forever, each one waiting for a resource held by another.

Writing correct programs with raw threads and locks is difficult. Fortunately, for divide and conquer algorithms there is a much simpler approach: if each task works on a **separate part of the data** and the results are combined only when the subtasks have finished, no synchronisation is needed beyond waiting for the subtasks. This is the model of the Fork/Join framework, presented in the next lesson.

## Summary

- Processor frequencies stopped growing because of power and heat; performance now grows by adding **cores**, and software must be designed to use them.
- **Concurrency** means dealing with several tasks whose executions overlap; **parallelism** means executing several tasks at the same time on several processors.
- **Processes** have their own memory; **threads** belong to a process and share its memory; **tasks** are units of work executed by threads.
- Shared memory requires synchronisation to avoid race conditions and deadlocks. Divide and conquer algorithms that work on independent parts of the data avoid most of these problems.
