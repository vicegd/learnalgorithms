Dynamic Programming: Classic Problems

This lesson applies the design steps of dynamic programming to several classic problems: counting combinations, the 0/1 knapsack problem, the change with any coin system, the cheapest travel on a river, and two problems on strings, the longest common subsequence and the edit distance. The implementations of the course examples are in the course repository.

What you will learn in this lesson
  • How to turn a recursive formula with overlapping subproblems into a table: Pascal's triangle.
  • How to solve the 0/1 knapsack problem optimally, fill its table by hand and recover which objects to take.
  • What a pseudo-polynomial algorithm is.
  • Two classic dynamic programming algorithms on strings: LCS and edit distance.

Combinations​

In mathematics, a combination is a way of selecting kkk things out of a larger group of nnn, where (unlike permutations) the order does not matter. For example, given three fruits (an apple, an orange and a pear), there are three combinations of two: apple and orange, apple and pear, and orange and pear. The number of combinations is the binomial coefficient:

C(n,k)=(nk)=n!k! (n−k)!C(n, k) = \binom{n}{k} = \frac{n!}{k!\,(n-k)!}C(n,k)=(kn​)=k!(n−k)!n!​

Computing it with factorials is risky: n!n!n! overflows a long for n>20n \gt 20n>20, even when the result is small. A better way uses the recurrence behind Pascal's triangle:

C(n,k)={1if k=0 or k=nC(n−1,k−1)+C(n−1,k)if 0<k<nC(n, k) = \begin{cases} 1 & \text{if } k = 0 \text{ or } k = n \\ C(n-1, k-1) + C(n-1, k) & \text{if } 0 \lt k \lt n \end{cases}C(n,k)={1C(n−1,k−1)+C(n−1,k)​if k=0 or k=nif 0<k<n​

(either a given element is in the selection, and we choose the other k−1k - 1k−1 among the remaining n−1n - 1n−1; or it is not, and we choose all kkk among the remaining n−1n - 1n−1).

Divide and conquer: exponential​

The recurrence translates directly into a recursive method:

public long combinationsRecursive(int n, int k) {
    if (k == 0 || k == n) return 1;
    return combinationsRecursive(n - 1, k - 1) + combinationsRecursive(n - 1, k);
}

Dynamic programming: Pascal's triangle​

The different subproblems are the values C(i,j)C(i, j)C(i,j) with 0≤i≤n0 \le i \le n0≤i≤n and 0≤j≤min⁡(i,k)0 \le j \le \min(i, k)0≤j≤min(i,k). Store them in a table, filled row by row, from top to bottom: each cell is the sum of the cell above and the cell above-left.

public long combinationsDP(int n, int k) {
    long[][] table = new long[n + 1][k + 1];
    for (int i = 0; i <= n; i++) {
        for (int j = 0; j <= Math.min(i, k); j++) {
            if (j == 0 || j == i)
                table[i][j] = 1;                                     // borders of the triangle
            else
                table[i][j] = table[i - 1][j - 1] + table[i - 1][j];  // Pascal's rule
        }
    }
    return table[n][k];
}

The 0/1 Knapsack Problem​

We met the knapsack problem in the greedy chapter. Now the objects cannot be fragmented: each object is either taken entirely or left. We have nnn objects, each with a weight wiw_iwi​ and a value viv_ivi​, and a backpack that can carry a total weight not exceeding WWW; we want to maximize the total value. We saw that no greedy heuristic is optimal for this version. Dynamic programming is.

If we take it, we gain viv_ivi​, and the remaining capacity j−wij - w_ij−wi​ must be used in the best possible way with the first i−1i - 1i−1 objects (the principle of optimality): V(i−1,j−wi)+viV(i-1, j - w_i) + v_iV(i−1,j−wi​)+vi​. The table gives the optimal value. int knapsack01(int maxWeight, int[] weights, int[] values) {
    int n = weights.length;
    int[][] v = new int[n + 1][maxWeight + 1];          // row 0: no objects, all zeros
    for (int i = 1; i <= n; i++)
        for (int j = 0; j <= maxWeight; j++) {
            v[i][j] = v[i - 1][j];                      // leave object i
            if (weights[i - 1] <= j)                    // take it, if it fits
                v[i][j] = Math.max(v[i][j], v[i - 1][j - weights[i - 1]] + values[i - 1]);
        }
    return v[n][maxWeight];
}

Complexity: pseudo-polynomial​

The table has (n+1)×(W+1)(n + 1) \times (W + 1)(n+1)×(W+1) cells, each computed in constant time: O(n⋅W)O(n \cdot W)O(n⋅W) in time and memory (memory can be reduced to O(W)O(W)O(W) by keeping a single row, at the cost of not being able to reconstruct the objects).

This looks polynomial, but it depends on the value of WWW, not on its size. WWW is written with about log⁡2W\log_2 Wlog2​W bits, so O(n⋅W)O(n \cdot W)O(n⋅W) is exponential in the size of the input, just like the naive greatest common divisor of the divide and conquer chapter. Such algorithms are called pseudo-polynomial: excellent when WWW is moderate (a few thousand), impractical when WWW is huge (for example, weights in grams of a cargo ship). No algorithm that is polynomial in the size of the input is known for the 0/1 knapsack problem.

The Problem of the Change​

In the greedy chapter we saw that always taking the largest coin that fits gives the fewest coins for the euro, but fails for other coin systems. Dynamic programming solves the problem for any coin system.

Problem. Pay an amount AAA with the fewest possible coins, choosing from nnn coin values c1<c2<⋯<cnc_1 \lt c_2 \lt \dots \lt c_nc1​<c2​<⋯<cn​, with an unlimited supply of each. We assume c1=1c_1 = 1c1​=1, so that every amount can be paid.

The subproblems and the recurrence​

Subproblems: let C(i,j)C(i, j)C(i,j) be the minimum number of coins needed to pay the amount jjj using only the first iii coin values. The answer is C(n,A)C(n, A)C(n,A).

Recurrence: for coin value cic_ici​ there are two options. Either we do not use it, and the best is C(i−1,j)C(i-1, j)C(i−1,j); or we use at least one coin of value cic_ici​, and then we still have to pay j−cij - c_ij−ci​, possibly with more coins of the same value, so the best is 1+C(i,j−ci)1 + C(i, j - c_i)1+C(i,j−ci​). The difference with the knapsack is in that last term: it stays in the same row iii, because a coin can be used many times.

C(i,j)={jif i=1 (only coins of value 1)C(i−1,j)if i>1 and j<cimin⁡(C(i−1,j),  1+C(i,j−ci))otherwiseC(i, j) = \begin{cases} j & \text{if } i = 1 \text{ (only coins of value 1)} \\ C(i-1, j) & \text{if } i \gt 1 \text{ and } j \lt c_i \\ \min\big(C(i-1, j),\; 1 + C(i, j - c_i)\big) & \text{otherwise} \end{cases}C(i,j)=⎩⎨⎧​jC(i−1,j)min(C(i−1,j),1+C(i,j−ci​))​if i=1 (only coins of value 1)if i>1 and j<ci​otherwise​

public int change(int amount, int[] coins) {        // coins sorted, coins[0] == 1
    int n = coins.length;
    int[][] c = new int[n][amount + 1];
    for (int j = 0; j <= amount; j++)
        c[0][j] = j;                                 // only coins of value 1
    for (int i = 1; i < n; i++)
        for (int j = 0; j <= amount; j++) {
            c[i][j] = c[i - 1][j];                   // do not use coins[i]
            if (j >= coins[i])
                c[i][j] = Math.min(c[i][j], 1 + c[i][j - coins[i]]);   // use it once more
        }
    return c[n - 1][amount];
}

Complexity. The table has n×(A+1)n \times (A + 1)n×(A+1) cells, each filled in O(1)O(1)O(1): O(n⋅A)O(n \cdot A)O(n⋅A) time and memory. As in the knapsack, it is pseudo-polynomial: it depends on the value of AAA. Only the previous row is needed, so the memory can be reduced to a single array of A+1A + 1A+1 positions.

With the table it is easy to check where the greedy algorithm fails: for the coins 1, 4, 5, 12, 20 and 50, it gives more coins than necessary for 10 of the amounts from 1 to 100, the first ones being 8 (greedy 5 + 1 + 1 + 1, optimal 4 + 4) and 15.

Cheaper Travel on the River​

A river has nnn docks, numbered from 0 (upstream) to n−1n - 1n−1 (downstream). At each one you can rent a boat to go to any other dock downstream; going upstream is impossible. A table of fees T(i,j)T(i, j)T(i,j) gives the price of a trip from dock iii to dock jjj, for i<ji \lt ji<j. A direct trip may cost more than a combination of shorter trips, changing boats at an intermediate dock. We want the minimum cost C(i,j)C(i, j)C(i,j) for every pair of docks i<ji \lt ji<j.

The subproblems and the recurrence​

The cheapest way from iii to jjj either goes directly, or stops for the first time at some dock kkk between them; then it must continue from kkk to jjj in the cheapest way, and also reach kkk from iii in the cheapest way (the principle of optimality):

C(i,j)=min⁡(T(i,j),  min⁡i<k<j(C(i,k)+C(k,j))),C(i,i)=0C(i, j) = \min\Big( T(i, j),\; \min_{i \lt k \lt j} \big( C(i, k) + C(k, j) \big) \Big), \qquad C(i, i) = 0C(i,j)=min(T(i,j),i<k<jmin​(C(i,k)+C(k,j))),C(i,i)=0

Each C(i,j)C(i, j)C(i,j) depends on pairs that are closer together, so the table can be filled by increasing distance j−ij - ij−i, or, as in the code below, with iii going from the last dock upwards and jjj from i+1i + 1i+1 downstream.

public int[][] minimumCosts(int[][] fee) {
    int n = fee.length;
    int[][] cost = new int[n][n];
    for (int i = n - 2; i >= 0; i--)
        for (int j = i + 1; j < n; j++) {
            int best = fee[i][j];                       // direct trip
            for (int k = i + 1; k < j; k++)             // first stop at k
                best = Math.min(best, cost[i][k] + cost[k][j]);
            cost[i][j] = best;
        }
    return cost;
}

Complexity. There are about n2/2n^2 / 2n2/2 pairs, and each one tries up to nnn intermediate docks: O(n3)O(n^3)O(n3) time and O(n2)O(n^2)O(n2) memory. It is the same idea as Floyd's algorithm for shortest paths between all pairs of nodes of a graph, simplified by the fact that the boats only go downstream.

Beyond the Course: Dynamic Programming on Strings​

Two classic problems show how dynamic programming handles sequences.

Longest common subsequence (LCS)​

A subsequence of a string is obtained by deleting some characters without changing the order of the rest. The longest common subsequence of two strings is the longest string that is a subsequence of both. For example, for ALGORITHM and ALTRUISM, an LCS is ALRIM, of length 5.

Subproblems: L(i,j)L(i, j)L(i,j) = length of the LCS of the first iii characters of aaa and the first jjj characters of bbb.

L(i,j)={0if i=0 or j=0L(i−1,j−1)+1if ai=bjmax⁡(L(i−1,j),  L(i,j−1))otherwiseL(i, j) = \begin{cases} 0 & \text{if } i = 0 \text{ or } j = 0 \\ L(i-1, j-1) + 1 & \text{if } a_i = b_j \\ \max\big(L(i-1, j),\; L(i, j-1)\big) & \text{otherwise} \end{cases}L(i,j)=⎩⎨⎧​0L(i−1,j−1)+1max(L(i−1,j),L(i,j−1))​if i=0 or j=0if ai​=bj​otherwise​

If the last characters match, they are part of the LCS; otherwise, one of them is not, and we keep the best of discarding either one. The table has (∣a∣+1)×(∣b∣+1)(|a| + 1) \times (|b| + 1)(∣a∣+1)×(∣b∣+1) cells: O(∣a∣⋅∣b∣)O(|a| \cdot |b|)O(∣a∣⋅∣b∣). The diff tool that compares versions of a file is based on this idea, applied to lines instead of characters.

Edit distance​

The edit distance (or Levenshtein distance) between two strings is the minimum number of single-character insertions, deletions and substitutions needed to transform one into the other. For example, KITTEN → SITTING needs 3 operations: substitute K by S, substitute E by I, insert G.
